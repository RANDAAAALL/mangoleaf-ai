# MangoLeaf AI Agent Instructions

## Next.js 16 source of truth

This repository uses Next.js 16.4.1. APIs, conventions, and file structure may differ from older Next.js versions. Before changing Next.js code or configuration, read the relevant installed guide under `node_modules/next/dist/docs/` and follow current deprecation notices.

## Project context

- The main application is an offline-first static-export PWA under `src/`.
- The supported mobile product is Android APK only, with portrait orientation requested on phones. Keep installation guidance and current product text Android-only, without iPhone/iPad instructions or browser PWA install prompts. Keep production and development browsers on every viewport limited to Home, About and Android installation. Do not mount browser scanning, History controls, Diagnostics or private backup workers; preserve legacy browser IndexedDB data without exposing or deleting it. Keep historical iOS evidence intact; diagnostic identification of an unsupported browser does not imply product support.
- Browser-side diagnosis uses TensorFlow.js model assets from `public/model/`.
- The retired browser compatibility storage uses Dexie/IndexedDB; the Java Android host uses SQLite and private photo files. Android bundles must fail closed if the trusted native bridge is unavailable, never fall back to IndexedDB. Manual report import/export UI and browser archive modules were retired by the maintainer on October 21, 2026. Preserve stored History and bounded native compatibility methods used by older bundles and cloud recovery.
- Public guidelines remain independent of diagnosis, saving, and backup. Both APK variants save reports in SQLite and photos in private files by default; do not initialize private Auth/enrollment/uploads from ordinary scanning, startup or reconnection before recovery-code setup. Explicit successful recovery-code creation persists verified credentials and enables automatic foreground/online backup without an extra saved-code confirmation, including when an older no-code installation had paused uploads; connecting an existing code also enables a fresh device unless a deliberate pause applies. Production uses its pinned production project; Debug uses testing. Preserve an existing anonymous owner/session and attach recovery credentials to that same Auth UUID rather than orphaning earlier backups. Preserve existing-code enablement, both `paused` and legacy `false` pause choices, and scoped pending-deletion retries even before a code exists. Failed new-code creation must leave uploads off; a failed existing-code connection must preserve the prior verified identity/settings. Keep Sign In/Register screens absent. Authenticate ownership through Supabase Auth/RLS; never trust a device UUID. Preserve existing reports, legacy metadata, hidden `pending-delete` rows, and native deletion records.
- History deletion atomically queues removal of manifest-paired copies in the connected backup. Keep jobs scoped to their project/vault, retry while foreground and connected even when uploads are paused, and acknowledge only after Storage and SQL succeed. Never use missing local rows or old tombstones to purge historical cloud data. Other devices with stale copies must pause uploads before deletion; this is not distributed deletion across devices.
- Keep scan photos as local Blobs. Never request legacy cloud URLs as a fallback. Existing cloud rows, private photos, users, and policies are preserved historical resources; changing or deleting them needs separate authorization. Any future cloud recovery must verify ownership rather than trust a device UUID.
- Serwist generates `public/sw.js` from `src/sw.ts` during builds.
- Android builds disable Serwist and stage isolated static assets through `bun run android:bundle`. The default copies committed model assets/constants without adopting uncommitted model overrides. Keep SQLite/photos/credentials outside replaceable OTA bundles. Current candidate host/bundle bounds are 8-8; ordinary Activity recreation must not activate updates. See `docs/versions/ANDROID_APK_VERSIONING.md` for native, cloud, signing, rollback, and verification steps. APK footers show the installed host's `hostVersionName` and active model; keep the independently updated web-bundle version in About. Browser footers retain app/model labels. The download page may show a production APK version only from a valid `Android APK v<version>` label on its verified published asset; never infer it from a web-release tag or installation hint.
- Keep permanent APK/OTA private keys and passwords outside Git. Production Release must verify its pinned signer, signed packaged assets and public OTA trust; Debug must exclude production OTA settings. Retain exact APK/OTA receipts under ignored `.tools/android-release/`, and require a portable protected key/password backup before publication. DPAPI credentials alone are tied to the original Windows account.
- Development public settings and default Android bundles use the pinned testing project from ignored `.env.testing.local`; `android:bundle --release` selects production. Preserve variant/host target checks and project-scoped private sessions/owner labels. Testing uploads require a connected recovery code and an eligible non-deleted photo report; ordinary History, including saved photos, creates no private identity until code creation is requested explicitly. Websites never enroll private backup owners or upload reports, including development. Dexie remains for legacy compatibility and isolated regression tests; use Debug APKs for supported scan testing. Wrong recovery credentials must preserve the current session; clearing the input must not disconnect it. Do not add cross-device deletion propagation. Never redirect automated scans to production or copy production reports/photos/users into testing.
- Keep `experimental.mcpServer: false` in `next.config.ts` so the development server does not expose `/_next/mcp` through public tunnels. This setting is independent of agent GitHub MCP connectors; allowed development origins are not authentication.
- Encode copied camera squares in the cancellable dedicated JPEG worker; terminate it on cancellation/backgrounding and preserve crop/quality in the bounded compatibility fallback. Keep first-result details with the APK entry so opening them cannot suspend the entire app. Phone website language controls show only the current EN or BIS code in both production and development; desktop header controls retain their existing labels. Local runtime model files were restored to adopted V4.5.0 on October 24; preserve V5 research records and do not reactivate that local override without explicit instruction.
- Keep pending Android camera permission prompts distinct from actual backgrounding so granting permission does not cancel its originating trusted camera request. Real background/closure must still stop the camera. Website launch intents may bring the existing APK activity forward; never load their URI data or extras into the bridge-enabled WebView.
- Treat related-app installation detection as a positive-only website hint, never Auth or bridge authorization. Keep user-tapped intents synchronous with a fixed package and same-origin guide fallback. Release-only native website association must match the public website origin; rebuild the APK when it changes. Debug must not advertise production installation.
- Use the reviewed Node 24 security floor in `.node-version` and `package.json`; run `bun run security:runtime` before Node-based tooling. Keep the CI selection and direct CLI checks aligned. Bun's reported Node compatibility version does not establish the installed Node executable's security state. Update the floor after reviewing later Node security releases.
- Keep the root Bun version in `package.json`'s exact `packageManager` field. Both CI jobs read it with `bun-version-file: package.json`; do not duplicate Bun version strings in the workflow. The separate `video/` project keeps its own package policy.

## Conventions

- Use lowercase kebab-case filenames for components and ordinary multiword modules, such as `legal-modal.tsx`, `scan-details-modal.tsx`, and `supabase-client.ts`.
- Use camelCase filenames for custom hooks, such as `useSync.ts` and `useInstallGuide.ts`, with matching `useSomething` exports.
- Keep React component exports in PascalCase, and give the inner function of a `memo(...)` wrapper the same name as the export so React DevTools and stack traces show the real component name.
- Group new components into the existing `src/components/` subfolders by screen area. Do not add files directly to `src/components/`. The folders exist for navigation and do not restrict imports; a component used by more than one area may be imported across folders.
- Put a reusable SVG in `src/components/brand/icon.tsx` as a new `IconName` entry instead of defining a local `<svg>` component in the file that first needs it. Let it inherit `currentColor` and take its dimensions from the `size` prop rather than hardcoding a fill or a `w-* h-*` class, so one call site cannot fix a colour or a size for every future caller.
- Keep the phone website header brand centered and its Home/About/open-install/language controls in `browser-bottom-nav.tsx` below 768px. Desktop website navigation stays in the header; native scanner navigation remains separate. Keep `devIndicators: false` so the development badge cannot cover phone Home; this does not suppress compile/runtime errors. APK About panels load with `Application`, not through a lazy import that can suspend into the global splash.
- Keep `src/app/page.tsx` as the build-target entry router. APK state, handlers and tab selection live in `src/components/layout/application.tsx`; the browser shell lives in `browser-landing.tsx`. Screen markup belongs in a tab component under the matching folder. Scanner test routes may be generated only into isolated test builds, never added to shipping source.
- Use the `@/*` alias for imports from `src/` when practical.
- Prefer `@/components/...` over relative `../` paths for cross-folder component imports so files survive being moved.
- Keep `README.md`, `SETUP.md`, and `AGENTS.md` at the repository root. Put other detailed project documentation in `docs/`.
- Keep the shared coworker review instructions in [docs/CODEBASE_REVIEW.md](docs/CODEBASE_REVIEW.md). Coworkers can reference that file with their own initial prompt after setup. Review analysis stays read-only; selected report/Q&A exports may use Desktop or ignored `docs/local-ignored-files/` under the guide's output rules.
- Keep current shared application release/version guidance in `docs/versions/PWA_VERSIONING.md`, native Android APK guidance in `docs/versions/ANDROID_APK_VERSIONING.md`, and model/training guidance in `docs/versions/AI_MODEL_VERSIONING.md`. Keep these guides short; full dated records belong in the matching `docs/versions/history/PWA_RELEASE_HISTORY.md`, `ANDROID_APK_HISTORY.md`, and `AI_MODEL_HISTORY.md`. Link instructions to the guides and historical evidence to its archive section; preserve existing section bookmarks. Keep dated performance reviews within `docs/PERFORMANCE.md` so findings, measurements, and their evidence limits stay together.
- Keep test instructions and physical-device checklists under `docs/testing/`, and treatment-guideline source reviews under `docs/treatment-guidelines/`. Preserve the `TESTING.md` and checklist filenames when linking to them.
- Treat `video/` as a separate project that happens to share this repository. It is a HyperFrames composition for the promotional video, with its own `package.json`, its own dependency tree, and its own `AGENTS.md`, which you should read before changing anything inside it. Nothing in it is imported by `src/` or copied into the static export. Run its scripts from inside `video/`, never from the root, and leave its `hyperframes` version pinned so renders reproduce. Commit the composition, its assets, and its lockfile, but never `video/node_modules`. Keep rendered output to one current file rather than adding a new cut alongside the old ones: video files cannot be diffed, so each one is stored whole and a later deletion does not shrink history.
- Update documentation when setup, architecture, environment variables, model versions, or release behavior changes.
- Maintain Supabase configuration, security, preservation, and rollback instructions in `docs/security/SECURITY-AND-SYNC.md`, alongside the other security guides. Keep private cloud backups under ignored `.tools/supabase-backups/`; tracked SQL and verification files must contain no real scan data, credentials, or session tokens.
- Do not manually edit generated files: `public/sw.js`, `.next/`, `out/`, `next-env.d.ts`, or `*.tsbuildinfo`.
- Do not commit `.env.local` or other secret-bearing environment files.
- Keep shared developer checks in tracked `tools/`; `/scripts/` remains local-only. Husky uses `lint-staged` and Prettier to format staged files before commits, then runs security, typecheck, lint, and formatting checks before pushes. `.github/workflows/ci.yml` repeats the checks alongside the production build only on pushes to `master`. Keep hook files LF-terminated and comments short enough for coworkers to scan.
- Use the pinned project Prettier and `.prettierrc.json`; respect `.prettierignore`. Run `bun run format` before verification when preparing source changes so the generated service worker reflects the formatted source. Keep ESLint's Prettier compatibility config last. Never run whole-project formatting from a Git hook or use formatting writes in CI.
- Install the pinned scanner with `bun run security:install` before security checks. Never print detected credential values or broadly allowlist real findings. Reserve `secrets/` and `confidential/` for local-only files; `.tools/` and Husky's generated `.husky/_/` must remain untracked. ESLint excludes local `.tools/` audit artifacts; tracked `tools/` remains checked.
- Do not turn version labels into environment variables. The app version comes from the `version` field in `package.json` via the `env` block in `next.config.ts`, and the model label is the `modelVersion` constant in `src/lib/constants.ts`. Keep both out of `.env.local`, `.env.example`, and hosting dashboard settings so a stale override cannot display the wrong version.
- Keep every user-facing string in `src/lib/translations.ts` with an entry in both the `en` and `bis` objects. Do not hardcode English in a component or helper, and do not rely on `toLocaleDateString` or other `Intl` formatting for Cebuano/Bisaya output, because browsers have no reliable locale data for it. Use `{n}` placeholder templates for counted labels so plural rules stay in the translation file.
- Preserve unrelated user changes and untracked work.
- Treat preserved Colab package snapshots as historical evidence, never as installation instructions. Keep their original bytes and run ledgers; record repository archive names in a separate provenance mapping. Keep byte-pinned receipts outside Git text conversion; any canonical ledger-hash mode must be explicit and must not rewrite original files. Review dependency advisories before executing a historical training workflow in a new environment. Keep unresolved dependency findings visible rather than suppressing the audit.
- Keep the hash-checked V5 Colab helper LF-terminated through its scoped `.gitattributes` rule. When its bytes change, update `EXPECTED_HELPER_SHA256` in both clean V5 notebooks together; preserve the original helper inside every existing frozen run.
- Reuse a saved duplicate diagnosis only when its `model_version` exactly matches the active model. Keep older and unlabeled legacy reports in History, but run current-model inference when their photo is uploaded again.

## Application tests and release candidates

- Follow `docs/testing/TESTING.md` for functional cases and automated R01–R04 scope. Use `docs/testing/PHYSICAL_RELIABILITY_CHECKLIST.md` as the fillable physical-device evidence record. Add short comments explaining non-obvious test behavior.
- Keep Playwright cases in `tools/e2e/*.pw.ts` so `bun run test:tooling` does not discover them as Bun unit tests. Use pinned Playwright through Node.js; Bun remains the package/build runner.
- `bun run test:e2e` runs the core desktop/mobile browser suite against an isolated production export. Keep it in CI on pushes to `master` only. Do not add the full browser suite or long reliability sessions to Husky pre-push.
- Run `bun run test:reliability` explicitly before release/research evaluation. R01 must invoke actual inference repeatedly; duplicate-report reuse does not measure prediction consistency. R03 is a 30-minute mixed-use session. Physical phones, native camera, airplane mode, OS/browser versions, and background behavior still require recorded manual checks.
- Use fresh browser contexts and the local mock backend for automation. Never direct automated scans at production Supabase. `.test-app/`, `test-results/`, `playwright-report/`, and `.playwright-mcp/` are generated local artifacts. Never deploy the isolated test build.
- Keep technical prediction diagnostics in developer console output and test reports. Preserve the existing optional fresh-result class-probability table and its copy-only formatting; saved History does not persist those table rows. Do not change model preprocessing/thresholds to make tests pass. Sort copies and format only presentation values so diagnostics cannot alter raw scores or rejection rules. New reports retain raw confidence; badges truncate to at most one decimal percentage and omit a trailing `.0`. Preserve previously rounded History values. Controlled UI scores and real-model observations must be identified separately; consistency and UI correctness do not establish model accuracy.
- Keep About diagnostics opt-in and bounded. Record controlled technical fields and safe error names, never photos, diagnosis results, report identifiers, credentials, raw messages, or URLs. Storage/export failures must not interrupt scanning or deletion. Distinguish a caller timeout from an underlying operation still settling, and record success only after the actual operation completes.
- Prepare candidate code, version labels, and affected documentation together before the final build. Candidate files may be committed/pushed for testing. Mark documentation as candidate/not released and state pending checks honestly; do not claim deployment or successful evaluation in advance. Record commit IDs and model hashes because multiple candidate attempts can share an intended version.
- Keep app and model versions independent. Testing infrastructure or reorganizing experiment guides does not by itself change the shipped app/model version. A new model also requires accuracy/OOD evaluation before adoption.
- For manual release approval on `master`, Vercel's Production branch tracking must have **Auto-assign Custom Production Domains** disabled. Confirm the dashboard setting; never assume documentation changed it. This creates staged production builds using Production environment variables, not a separate database.
- Require CI and the approved release validation before promotion, including applicable reliability checks. Use the physical-device checklist when physical-device evaluation is part of that scope. Promote the exact tested deployment, verify the live version, and tag/release its tested commit. A GitHub Release does not control Vercel deployment. Rebuild and repeat affected checks if source, version labels, model files, or build settings change after testing.
- Release shortcuts preserve these gates: production USB installation requires the matching verified APK/receipt and public signer pin; tag creation requires an explicit full approved commit with a matching app version. Keep tag pushes explicit and limited to the selected tag; never infer CI/release approval, force an existing tag, or reuse an old release manifest for a new candidate. Run R03 from the intended source copy and retain its input hashes.
- Keep model-training documentation under `docs/model-training/experiment/v{n}/` for candidate workflows and `docs/model-training/non-experiment/v{n}/` for historical or adopted trials. Put each version's `TRIAL_v{n}.md` beside its optional `artifacts/` and `figures/` folders; use underscores for decimal versions in report filenames (for example, `TRIAL_v4_1.md`). V3.1 also keeps a separate original-weight threshold guide. Keep candidate notebook workflows and completed experimental evidence under `notebooks/experiment/<notebook-version>/`, and current adopted or older historical notebooks under `notebooks/non-experiment/<notebook-version>/`. On explicit model adoption, move that version's preserved templates and completed notebooks to `notebooks/non-experiment/<notebook-version>/` and its trial/evidence folder to `docs/model-training/non-experiment/v{n}/`. The `non-experiment/` grouping includes the current adopted model as well as older models; it does not establish deployment or field accuracy. Preserve notebook cell contents, outputs, original artifact identities, and historical results; record the adoption identity and any changed configuration hashes separately. Workflow versions never imply an app or model version. Update relative links and architecture trees when moving either group, and distinguish repository adoption from pending production deployment.

## Documentation maintenance

Every implementation task must include a documentation-impact review before it is considered complete. Update the documents affected by the change in the same task; do not postpone known documentation updates to a later commit.

| Change made                                                                                                         | Documentation or metadata to review and update                                                                                             |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Installation steps, prerequisites, Supabase resources, commands, or environment variables                           | `SETUP.md`, `.env.example`, and the README quick start when relevant                                                                       |
| Application layers, data flow, storage, synchronization, service worker, deployment model, or important directories | `docs/ARCHITECTURE.md`                                                                                                                     |
| User-visible feature, workflow, important fix, milestone, or completed project task                                 | `docs/PROGRESS.md`                                                                                                                         |
| Performance behavior, caching, bundle loading, image processing, inference, memory, or network optimization         | `docs/PERFORMANCE.md`                                                                                                                      |
| App version, model version, release process, tags, or notebook-version policy                                       | The matching guide and dated record under `docs/versions/`, `package.json`, `src/lib/constants.ts`, and other displayed version references |
| Model training, dataset, class mapping, evaluation metrics, or exported model files                                 | The applicable trial under `docs/model-training/`, model guide and dated record under `docs/versions/`, and `docs/PROGRESS.md`             |
| File or directory rename                                                                                            | All imports, scripts, configuration, Markdown links, project trees, and documentation references to the old path                           |
| New long-lived convention or recurring agent workflow                                                               | `AGENTS.md`                                                                                                                                |

Use these rules when maintaining documentation:

- Keep historical entries intact; add a new dated or versioned entry instead of rewriting past results as if they happened differently.
- In `docs/PROGRESS.md`, group updates from the same exact date under one daily heading with topic bullets. Preserve historical content and old heading anchors when consolidating; date ranges remain separate.
- Use the same date/topic layout for the history in `docs/testing/TESTING.md`, oldest first. Keep current test instructions separate from dated evidence, and keep the blank physical checklist and fictional sample in workflow order. Preserve existing bookmarks, measurements, and evidence limits when reorganizing.
- Update only documents affected by the change. Do not create progress noise for formatting-only edits, comment-only clarification, or generated-file changes unless they affect project behavior or maintenance instructions.
- Ensure examples describe the current repository and installed dependency versions rather than generic templates.
- Check local Markdown links and search for stale filenames or version labels after moving or renaming files.
- If no documentation update is needed, explicitly confirm that the documentation-impact review was completed in the final handoff.

## Verification before commit

Run these commands in order and require all three to pass:

```bash
bun run typecheck
bun run lint
bun run build
```

The build uses webpack and creates a static export in `out/`. Treat build failures, service-worker generation failures, type errors, and lint errors as blockers before committing.

## Native branding and installer delivery

- Keep Android launcher artwork as transparent vectors with an adaptive background supplied separately. System splash resources use the transparent foreground directly; do not restore a precomposed square, circle or shadow inside the leaf. Android/Samsung may still apply their own outer mask. Resource changes need a new native version/code and installer; OTA changes only web assets.
- Production APK delivery uses the fixed-repository `/apk/<tag>/mangoleaf-ai.apk` Vercel rewrite and a validated release tag. Never accept a download origin, repository or arbitrary filename from URL parameters. Keep installer requests NetworkOnly in the service worker, preserve the exact-release fallback, and do not add APK binaries to `public/` or Git. Verify the deployed bytes/hash and Android browser completion before publication.
